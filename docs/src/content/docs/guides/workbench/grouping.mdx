Grouping rows in the data grid works by one column, with group header
rows whose counts and totals are computed **on the server**, not by summing the
rows currently on the page. This keeps totals correct on large tables.

## Two-tier fetch

- **Collapsed view** issues one grouped
  [aggregate](/BifrostQL/guides/aggregate-queries/) query returning group keys, a
  count, and an optional sum over one numeric column (any numeric scalar,
  `BigInt` and `Decimal` included). It reads at most 1,000 groups, taken in key
  order; when more match, the summary says "First 1000 groups" and notes that a
  count sort ranks only those.
- **Expanding a group** fetches only that group's member rows, with the group
  key merged into the active filter through the query-builder helpers. A `NULL`
  group key is its own labeled group, fetched with a `_null` filter (not
  `_eq: null`).

No total anywhere is computed client-side; TanStack's client aggregation is not
used for header values.

## URL is the source of truth

Grouping state round-trips through a `gb` URL parameter, mirroring the `cf`
column-filter parameter: setting grouping updates the URL, and loading that URL
restores the same grouping. There is no parallel component state driving the
query, so **switching tables clears grouping** — no `gb` value from the previous
table leaks into the new table's query.

With an active column filter or header filter and grouping, the filters
compose first and then the grouping, so totals match the filtered SQL. The
group query uses the same filter builder as the grid; a filter the grid can't
apply shows its error and no grouping request is sent. A relationship drill
grid ignores the main grid's filters and grouping.
